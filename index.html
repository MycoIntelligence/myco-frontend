the whole system.

Illustrative evidence record · payment retry

01 Changepayment-retry.ts

Before

After

In retryPayment(), the retry now replaces the payment object. Whether that is safe depends on what the restored object preserves.

02 Required byPAY-42

Payment retries must preserve the original idempotency key.

03 Depends onretry-state.ts

return { amount: snapshot.amount }

The restored object has no idempotencyKey field. In this example, createPaymentIntent() generates a new key when none is passed, allowing a separate payment.

Hypothesis

Replacing the object may drop the original key and allow a duplicate charge.

04 Validation · illustrative assertion

original.idempotencyKey = "pay_9182"
retryRequest = restore(snapshot)
retryRequest.idempotencyKey ?? null

Required by PAY-42

Expected: "pay_9182"

Observed: null

Validated signal

Retry can result in duplicate customer charges.

The changed assignment drops the original idempotency key before createPaymentIntent(). A new key allows a separate payment instead of deduplicating the original request. Preserve the original key when restoring the payment for retry.
